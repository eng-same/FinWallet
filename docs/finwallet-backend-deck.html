رحلة داخل الكود: من طلب HTTP بسيط إلى تنفيذ منطق البنك — وشرح للأنماط اللي اخترناها: Clean Architecture، وCQRS، وFeature Slices، وMediatR.

01 · الصورة الكبيرة

ليش قسّمنا المشروع إلى خمسة مشاريع؟

كل مشروع (Class Library) له مسؤوليّة واحدة واضحة. القاعدة الذهبية: الكود المهم (قوانين البزنس) لا يعرف شيئًا عن قاعدة البيانات ولا عن الإنترنت.

Domain
القلب — الكيانات والحالاتWallet · Transaction · Enums. قوانين خام، بلا تقنية.
يعتمد على: لا شيء
Application
العقل — كل الـ Use CasesCommands · Queries · Handlers · Validation · DTOs
يعتمد على: Domain + Contracts
Contracts
لغة التواصل — رسائل RabbitMQالأحداث المشتركة بين الـ API وخدمة البنك
يعتمد على: لا شيء
Infrastructure
الأدوات التقنية — التنفيذ الفعليPostgres · JWT · RabbitMQ · OpenTelemetry
يعتمد على: Domain + Application
Api
الواجهة الخارجية — نقطة التشغيلControllers · Program.cs · Middleware
يعتمد على: Application + Infrastructure
02 · اتجاه الاعتماديّة

الاعتماديّات دائمًا نحو الداخل

التفاصيل التقنية تعتمد على البزنس — وليس العكس. لو غيّرنا قاعدة البيانات، نعدّل Infrastructure فقط، ويبقى القلب سليمًا.

←
Infrastructureالتقنية
←
Applicationالمنطق
←

الفايدة العملية: الـ Application تعتمد على IApplicationDbContext (وعد/عقد)، مش على الكلاس الحقيقي. القلب لا يعرف أصلًا أننا نستخدم PostgreSQL — وهذا هو مبدأ عكس الاعتماديّة (Dependency Inversion).

Command · أمر

يغيّر الحالة

«اشحن محفظتي»

04 · مفهوم

Feature Slices — التنظيم حسب الميزة

بدل تجميع كل الكنترولرات في مجلد وكل الخدمات في مجلد آخر (التنظيم التقليدي حسب النوع التقني)، جمّعنا كل ما يخص ميزة واحدة في مكان واحد.

الفايدة: تبي تشتغل على المحفظة؟ كل شغلك في مجلد Wallets/. ما تحتاج تفتح ٦ مجلدات متفرّقة — الميزة «شريحة رأسية» مكتملة بذاتها.
Features/
Features/
├── Wallets/     // المحفظة
├── Transfers/   // التحويلات
├── Auth/        // الدخول والتسجيل
└── Admin/       // لوحة الأدمن
05 · مفهوم

الوسيط (Mediator) — مكتبة MediatR

حلقة الوصل بين الكنترولر والمنطق. الكنترولر يقول فقط: «عندي هذا الطلب، وصّله للجهة المسؤولة» — وهو لا يعرف مَن سينفّذه.

Controllerيرسل Request
←
MediatRيبحث عن المعالج
←
Handlerينفّذ المنطق
فصل تام

اللي يطلب لا يعرف اللي ينفّذ.

كنترولر نحيف

سطر واحد فعلي، بلا منطق بزنس.

قابل للاختبار

نختبر الـ Handler وحده بلا HTTP.

06 · مثال عملي · الخطوة ١

الكنترولر: مجرّد «بوّاب»

الطلب GET /api/wallets/my-wallet — لاحظ كم هو نحيف: سطر واحد فعلي.

FinWallet.Api/Controllers/WalletsController.cs
[Authorize]
public sealed class WalletsController : ApiControllerBase
{
    [HttpGet("my-wallet")]
    public async Task<ActionResult<WalletDto>> GetMyWallet()
    {
        // ١) يبني الرسالة  ٢) يرسلها للوسيط  ٣) يرجّع النتيجة
        var result = await Mediator.Send(new GetMyWalletQuery(UserId));
        return Ok(result);
    }
}
لا يوجد أي منطق بزنس هنا إطلاقًا — هذا مقصود.
من أين جاء UserId وMediator؟ من الكلاس الأب ApiControllerBase، الذي يستخرج هوية المستخدم من الـ JWT تلقائيًا ويجلب الوسيط عند الحاجة.
07 · مثال عملي · الخطوة ٢

الرسالة والمعالِج: هنا المنطق الفعلي

FinWallet.Application/Features/Wallets/Queries/WalletQueries.cs
// ١) الرسالة: مجرّد «طلب» يحمل بيانات، وينتظر ردًّا من نوع WalletDto
public sealed record GetMyWalletQuery(Guid UserId) : IRequest<WalletDto>;

// ٢) المعالج: MediatR يربطه بالرسالة تلقائيًا
public sealed class WalletQueriesHandler : IRequestHandler<GetMyWalletQuery, WalletDto>
{
    private readonly IApplicationDbContext _db;   // ← Interface، مش الكلاس الحقيقي

    public async Task<WalletDto> Handle(GetMyWalletQuery request, CancellationToken ct)
    {
        var wallet = await _db.Wallets
            .FirstOrDefaultAsync(w => w.UserId == request.UserId, ct);

        if (wallet == null)
            throw new FinWalletException("WALLET_NOT_FOUND", "Wallet not found.");

        return new WalletDto(wallet.Id, wallet.WalletNumber, wallet.Balance, ...);
    }
}
لماذا Interface؟ الـ Application تعتمد على «وعد» فقط. الكلاس الحقيقي في Infrastructure — فالقلب لا يعرف تفاصيل قاعدة البيانات.
08 · مفهوم

لماذا نرجّع WalletDto وليس Wallet؟

Entity

كيان قاعدة البيانات. قد يحمل علاقات داخلية وبيانات حسّاسة لا نريد كشفها للخارج.

09 · مثال أعقد · التحقّق

الأمر يأتي معه «مُدقّق» تلقائي

مع كل أمر نكتب Validator بمكتبة FluentValidation. لكن مَن يشغّله؟ (الجواب في الشريحة التالية 👈)

Features/Wallets/Commands/RequestWalletTopUpCommand.cs
public sealed record RequestWalletTopUpCommand(
    Guid UserId, decimal Amount, string Currency, string? Description
) : IRequest<TransactionDto>;

public sealed class RequestWalletTopUpCommandValidator
    : AbstractValidator<RequestWalletTopUpCommand>
{
    public RequestWalletTopUpCommandValidator()
    {
        RuleFor(x => x.Amount).GreaterThan(0)
            .WithMessage("Amount must be greater than zero.");
        RuleFor(x => x.Currency).Equal("LYD")
            .WithMessage("Currency must be LYD.");
    }
}
10 · القوّة الحقيقية

خط أنابيب MediatR (Pipeline Behaviors)

قبل أن يصل الطلب للـ Handler، يمرّ عبر سلسلة «طبقات وسيطة» — نكتبها مرة، وتنطبق على كل الأوامر آليًا.

Request→ Logging→ Exception→ Validation→ Handler→ Response
Common/Behaviors/ValidationBehavior.cs
public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, ...)
{
    // شغّل كل المدقّقات المرتبطة بهذا الطلب
    if (failures.Count != 0)
        throw new ValidationException(failures);  // ارفض قبل الوصول للـ Handler

    return await next();  // كل شيء تمام؟ كمّل للطبقة التالية
}
الفايدة الضخمة: الـ Handler الذي يشحن المحفظة لا يهتم بالتحقّق إطلاقًا — يصله الطلب مضمونًا أنه صحيح. هذا نمط Cross-Cutting Concerns: صفر تكرار.

وظيفة كل مشروع

المشروعمسؤوليّتهأهم المكتبات

Contractsلغة التواصل. أحداث RabbitMQ المشتركة.—
Infrastructureالأدوات. DbContext الحقيقي · JWT · الرسائل.Npgsql · MassTransit · JwtBearer
Apiالواجهة والمشغّل. Controllers · Program.cs.ASP.NET Core · Serilog
Program.cs هو «لوحة الكهرباء»: يجمع كل القطع في حاوية الـ Dependency Injection — AddApplication() وAddInfrastructure() — فيحصل كل Handler على ما يحتاجه تلقائيًا.
12 · الخلاصة

ليش هذه الطريقة؟ كل نمط يحلّ مشكلة

CA
Clean Architecture

البزنس لا يتعلّق بالتقنية → سهل تغيّر قاعدة البيانات أو تختبر بدونها.

CQ
CQRS

فصل القراءة عن الكتابة → كل نوع نظيف ومركّز.

FS
Feature Slices

كل ميزة في مجلد واحد → سهل تلاقي شغلك وتضيف ميزة.

MD
MediatR

فصل الكنترولر عن المنطق → كنترولرات نحيفة وHandlers مستقلّة.

PB
Pipeline Behaviors

التحقّق والتسجيل والأخطاء في مكان واحد → صفر تكرار.

DTO
DTOs

فصل الشكل الداخلي عن الخارجي → أمان وتحكّم بما يُعرض.

القاعدة الذهبية: كل جزء يعرف أقل شيء ممكن عن غيره. الكنترولر لا يعرف الـ Handler، والـ Handler لا يعرف قاعدة البيانات، والـ Domain لا يعرف أي شيء — وهذا الفصل هو ما يجعل المشروع سهل الصيانة والتوسّع والاختبار.
